:::tldr
I built PretrainGym during the Prime Intellect RL Residency. An agent is given the goal to curate a pretraining corpus. It gets a fixed model implementation, a 400M-token budget and a tool for scoring draft mixtures.  The environment then trains the model on that corpus and scores its loss on a held-out eval. I evaluated three agents: GLM-5.3 in Pi, Kimi K3 in Kimi Code, and GPT-6.1 Sol in Codex. Every run is in the [trace viewer](/traces/pretraingym/), turn by turn.
:::

## Why build this

Recursive self-improvement (RSI) is currently being hyped to the moon and back.[^hype] The question is whether a model can train a better version of itself.

<Tweet name="imjustnewatai" handle="imjustnewatai" date="Oct 9, 2026" url="https://x.com/imjustnewatai/status/2108662320708698289" avatar="/assets/blog/x-imjustnewatai.jpg" caption="The aforementioned hype.">

Some rumors I've heard. I'll start with Google, then Anthropic and OpenAI.

Google: Insiders say Google has either cracked RSI (recursive self-improvement) or is very close. Their pace has picked up fast in recent months. They went from GPT-5 level to Opus 5.5 level in months, and speculation is that RSI made that possible.

Anthropic: About a week ago, Anthropic started a new pretraining run. It is not Fable 5.5 but what would become Fable 6, or something bigger, to catch up to OpenAI's Bel.

OpenAI: Bel (it may have another codename) is the model behind the math results OpenAI published a few days ago, and RSI apparently helped there too.

From what I'm hearing, OpenAI, Anthropic, and Google are all very close to cracking RSI or already have. It will get scary and exciting at the same time.

</Tweet>

People claim that RSI has been solved or will be very soon. There are several related works that tackle RSI from different angles:

- **Absolute Zero:**[^azr] a model improves its reasoning by writing its own practice problems and solving them, with no human-written training data.
- **Darwin Gödel Machine:**[^dgm] a coding agent improves by rewriting its own code, keeping an archive of past versions to branch from. That took it from 20% to 50% on SWE-bench.
- **PostTrainBench:**[^ptb] asks whether agents can handle one stage of building a model, post-training. Each agent gets four small base models, one H100 and 10 hours.
- **Autonomous nanoGPT speedrunning:**[^speedrun] asks whether agents can improve the recipe that trains a model. Prime Intellect ran an autoresearch loop on the speedrun's optimizer track for about two weeks. A follow-up ran 153 autonomous runs across 18 frontier models, each with 8×H200s, no internet access and up to eight days.[^pimeasure] No run found a fundamentally new method, but the models differed sharply: the best, Claude Fable 5, closed about 82% of the gap between the baseline and the human record.
- **RSI Bench:**[^rsibench] Scale's benchmark for the skills RSI would need across every stage of frontier AI development. It concurrently developed a pretraining data curation task, although at a smaller scale.
- **Vals RSI Index**[^vals] and **DeepRSI:**[^deeprsi] track how close agents are to doing the research that builds the next model, using longer research tasks.
- **How to Measure RSI:**[^elasticity] the Elasticity Institute lists eight things frontier labs could report to show how fast RSI is happening. One is pretraining compute efficiency, meaning loss as a function of compute.

These works reveal a great shift in research interest towards RSI. To help contribute to this body of work, I wanted to see how well models could take on arguably the least understood part of pretraining: the data mix. The nanoGPT speedrun[^nanogpt] and OpenAI's Parameter Golf challenge[^paramgolf] both fix the data (FineWeb) and ask how good a training recipe can get. PretrainGym does the reverse. It fixes the training recipe, a speedrun-style trainer, and asks:

> Can an agent curate pretraining data? If so, how well can it perform?

## The gym

<PretrainGymLoop/>

Every version has the same shape. The agent gets a starter prompt, a token budget, a fixed model implementation and optimizer, and a self-scoring tool, and it can search and download Hugging Face datasets. It writes a `manifest.json` that says which datasets to use and how to weight them. The harness then trains the model on 400M tokens[^budget] drawn from the manifest. Before training, it removes documents that match the held-out eval. The model is nanoGPT-style with 11 layers and 768 dimensions, using the SmolLM2 tokenizer[^smollm2] (49,152 tokens). The reward is

<Tex block tex={String.raw`\text{reward} = \text{performance} - \text{leakage}, \qquad p = \frac{10.8027 - L}{10.8027 - 3.28}`} />

where performance is <Tex tex="p^2" /> when <Tex tex="p \ge 0" />, and <Tex tex="L" /> is the trained model's cross-entropy on the held-out eval. Since pretraining loss typically has the largest gains in the initial steps, performance is squared so that loss gains closer to the target loss are rewarded more. The two constants are anchors. 10.8027 is <Tex tex="\ln(49{,}152)"/>, the loss of guessing uniformly over the vocabulary, and 3.28 is the speedrun's target loss,[^nanogpt] so a reward above 1 means the model beat the speedrun target. Since we measure performance by evaluating loss on a held-out set, the agent can achieve a very simple reward hack by including the held-out set in its training data. The leakage term takes care of this by negatively impacting the reward based on the proportion of the submitted manifest that matches data from the held-out set. This is done using Allen AI's decontamination tool: decon.[^decon]

## Building the environment

Preventing reward hacking was the hardest part of building this environment (as is the case with most environments[^mimo]). The initial version gave the agent a lot to work with: it could read the training script (from the nanoGPT speedrun), browse the web and use the Hugging Face CLI, and the held-out set was the nanoGPT speedrun's FineWeb validation file. This setup led models to read the training script, recognize it as the nanoGPT speedrun's, search the web for the speedrun, and guess that the held-out set was FineWeb validation, since that's what the speedrun is scored on. From there, models figured out that the best manifest was simply FineWeb.

For the next version of the environment, I took away web access and hid the training script, leaving the Hugging Face tools and the self-scoring tool. GLM-5.3 worked out what the held-out set looked like anyway, through `self_score` itself. It never named FineWeb validation. Instead, it trained the model on one corpus at a time at the full budget, and raw FineWeb came out on top every time:

It then submitted a manifest with a single source, `HuggingFaceFW/fineweb`, and had the highest reward of 1.070.

For the final iteration of the environment, I changed the held-out set to Paloma,[^paloma] which averages loss over 12 sources ranging from C4 and Reddit to code, papers and Wikipedia. This means no single corpus could match the held-out set distribution the way FineWeb matched FineWeb validation. `self_score` measured loss on a validation split of Paloma, the final score used Paloma's test split, and documents matching either split were removed before training. I removed Hugging Face CLI access and created custom tools so that the agent could search, inspect, and download data without ever having access to more than it needs to.

The final setup for the evaluation is the following. Each agent works in a sandbox with no GPU and no network. Five tools run on an MCP server: search, inspect and fetch Hugging Face datasets, search papers, and `self_score`. A source in the manifest is either a Hugging Face dataset pinned to a commit from 2025 or earlier, or a local `.jsonl` shard the agent builds from such datasets. `self_score` trains the model on a draft manifest at whatever token budget the agent asks for, and reports the reward terms and training statistics, including the loss on a validation split of the hidden eval. Only one job runs at a time, and a full 400M-token job takes roughly an hour. Each agent gets 500 turns and no wall-clock limit. A time limit would make the score partly a measure of hardware, since faster GPUs would let an agent fit more `self_score` jobs into the same time.[^timeouts] In this iteration of the environment, models could finally focus on data curation instead of finding ways to cheat the evaluation.

What followed was careful work aimed at the wrong target. 54 of its 56 dataset searches were for exams and benchmarks. It estimated that AGIEval made the eval roughly 30% Chinese (later 41%) and fetched C-Eval, CMMLU, GaokaoBench, CMExam, DISC-Law and a dozen more. It also matched MMLU subjects to sources, using CaseHOLD for professional law and ETHICS for moral scenarios. Over the run it built 23 local datasets totaling about 925M tokens.

It also recovered AGIEval's exact prompt templates and rendered training questions in them. Its own 8-gram contamination filter then flagged nearly all of them, because the template text itself appears in the eval. So it changed the templates just enough to break every match: "Among A through E" became "Among A to E." The questions came from training splits and were decontaminated, so no eval content went into the corpus. Still, this is an agent working out how a contamination screen matches text and shaping its data to get past it.

Its first full-budget mixture was conservative, because GLM submitted it before building most of the exam data: about 54% general text (FineWeb-Edu, Cosmopedia, Wikipedia), 42% math, and 4% multiple-choice reading. It scored 3.2295. Then GLM ran the full bet: 18% Chinese plus more exam formats, with its four Hub sources (FineWeb-Edu, Cosmopedia, OpenWebMath and Wikipedia) cut from 64% of the mix to 44%. That run did worse, at 3.3065, even though its training loss was much lower. GLM noticed and did the arithmetic: if 41% of the eval were Chinese, a model trained on no Chinese couldn't have scored 3.23. It briefly doubted the theory, but the conclusion it carried forward was a patch: the eval must be mostly English, so more general English text was better.

That was right as far as it went, but it never reopened the question of what the eval actually was. GLM's last dataset search came at minute 125. Its remaining runs rearranged the four Hub sources and the shards it already had, and none of them beat the first mixture. It did run them carefully. One run was a clean ablation that changed a single variable. It traced its 0.00115 leakage penalty to the Hub web sources by elimination. It also kept `manifest.json` byte-identical to its best run the whole way, so its final score is its best score.

It then built its own data pipeline, the most engineering any of the three agents did. The pipeline normalizes and deduplicates text and cuts it into paragraph-aware fragments short enough to fit the model's context. ## Comparison to humans

Human data teams approach the same problem very differently. Marin's Datakit pipeline,[^marin] for example, works at the scale of trillions of tokens:

- **Clean:** start from 25.25T tokens (18.71B documents) across 152 openly licensed datasets, then remove 2.13T tokens of duplicates and decontaminate 13.66B tokens that overlap benchmarks.
- **Bucket:** split the result into 40 topics and 5 quality bands, giving 200 buckets.
- **Search:** run about 1,000 small proxy experiments, fit a regression that predicts benchmark performance from the bucket weights, and choose one weight per bucket.

Poolside's AutoMixer, described in its Laguna technical report,[^laguna] works the same way at a smaller scale:

1. Perturb a mixture over more than 50 dataset groups.
2. Train a swarm of about 60 proxy models on the variations. Each is a roughly 0.5B-parameter mixture-of-experts model trained on about 60B tokens.
3. Fit a surrogate regressor for each capability.
4. Optimize the weights against those regressors.

Kimi K3's 26 hours of mostly full-budget runs were the closest to the human methods. With far more compute and time, an agent running this kind of automated research loop on data curation would probably do very well.[^mirrorcode]

## Takeaways

**Agents aren't yet efficient at this kind of self-improvement.** Every agent got a loss close to the target loss. However, the agents wasted turns polling or exploring a poor research direction before locking in on a better target.

**Humans are still better at data-mixing.** Human methods try to be as principled as possible with clean deduplication, decontamination, and regressor fitting. The agents had solid methods but were often empirically wandering.

**Open-weight models are much better than we think!** Kimi K3 in particular had a solid research process, and both it and GLM-5.3 beat out GPT-6.1 Sol.

## What's next

- **Close the gap with real research:** give agents constrained web access rather than none. It would be interesting to see whether agents use existing datasets or build their own web crawler.
- **Multi-agent scaling:** with the recent successes of multi-agent systems,[^navier] [^primerust] I am very curious how they would do on RSI-related tasks.
- **Train with RL** on the environment, rather than only evaluating. Rollouts can run past 24 hours, though, which makes that hard.
- **Change the target:** use different eval distributions. It is also an interesting research direction to see if we give the agent a target domain like mathematics, how well it can hill-climb data curation for mathematics models.
- **More compute:** for the agent's own experiments and for longer horizons.
- **Other model scales:** check whether a mixture's advantage holds up, although Microsoft's MAI-Thinking-1 technical report shows that data mixtures may not hold rank invariance at different scales.[^mai]
- **More harnesses and models,** with several rollouts each.
